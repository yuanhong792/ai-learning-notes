01 / FOUNDATIONS
壹

AI 认知 · 先把底层逻辑弄明白

Token、上下文、幻觉、RAG 与技术选型——这几讲决定你后面所有判断。

4 讲
01大模型到底怎么「想」的：Token 与上下文窗口

模型不读「字」，它读的是被切碎的 Token；它能记住的全部内容，就是那个有限的上下文窗口。

  • Token 是模型处理文本的最小单位，中文大致一个字对应 1～2 个 Token。输入输出都算钱，长文档的成本主要来自这里。
  • 上下文窗口是一次对话里模型能「同时看见」的上限。超出部分会被挤掉，它不是记性差，是真没看见。
  • 所以「给足背景」和「别塞垃圾」同样重要。塞满无关内容，反而会把关键指令的权重稀释掉。
  • 实用做法：每轮只保留任务相关的背景、约束和最新结果，长对话定期做一次摘要重启。

✦ 记住：不理解这两个词，后面所有调优技巧都是碰运气。

# 基础概念# Token# 上下文
02幻觉不是 Bug，是工作机制的一部分

指望模型自己不出错，是最常见也最贵的误解。

  • 生成式模型本质是概率续写。当知识缺口出现时，它会补出一个「看起来最合理」的答案，而不是回答「我不知道」。
  • 越是需要精确事实的场景（数字、法条、人名、日期、版本），越不能只靠模型裸答。
  • 三道防线：给它可查的资料、要求逐条标注出处、对关键结论做人工或程序复核。
  • 把「不确定就说不确定」写进提示词有用，但只能降低概率，不能当兜底。

✦ 记住：模型的目标是「接着写下去最像样的话」，不是「说真话」。

# 幻觉# 可靠性# 事实核查
03RAG：给模型外挂一本随时能翻的书

检索增强生成的思路很朴素：先找资料，再让模型照着资料回答。

  • 流程是：把文档切片并向量化存起来 → 提问时检索出最相关的片段 → 连问题一起塞给模型 → 模型基于片段作答。
  • 它解决两件事：私有数据进不了模型参数、以及模型知识有截止时间。
  • 效果天花板往往不在模型，而在切片粒度和检索命中率。答不准时先查「检索回来的片段对不对」。
  • 适合：产品手册、内部规范、个人笔记库。不适合：需要全局推理或精确计数的任务。

✦ 记住：不改模型，也能让它回答你自己的资料。

# RAG# 知识库# 检索
04提示词 / RAG / 微调，到底该选哪个

优先级永远是：先提示词，再 RAG，最后才考虑微调。

  • 提示词：改表达方式、给示例、定输出格式。成本最低，能解决大部分「答得不对味」的问题。
  • RAG：模型不知道你的私有资料，或知识需要频繁更新。这是知识库类需求的正解。
  • 微调：要固定某种风格、格式或稳定完成一类窄任务，且已有足够高质量样本。它不擅长灌输新知识。
  • 常见误区：拿几百条文档去做微调来「教知识」，又贵又不如直接做检索。

✦ 记住：一张表省下几周的瞎折腾。

02 / PROMPTING
贰

提示词 · 把话说清楚，AI 才听得懂

四件套、先计划后动手、少样本示例、模板化——提示词是可复用的工程资产。

4 讲
01一条好提示词的四件套

把模糊的「帮我写一下」换成结构化的四段，输出质量会有肉眼可见的变化。

  • 角色：告诉它站在谁的位置思考（「你是一位熟悉门店运营的文案」比「你是助手」有用）。
  • 任务：一句话说清交付物是什么、给谁看、用来干什么。
  • 约束：字数、语气、禁用词、必须包含的字段、输出格式。边界越具体，返工越少。
  • 示例：给 1～3 个「好输出长这样」的样本，比讲十句道理都管用。

✦ 记住：角色、任务、约束、示例——少一件，效果就飘。

# 提示词结构# 入门
02让它先写计划，再动手

直接要成品，模型容易在半路跑偏；先要计划，等于给它一次自我校准的机会。

  • 第一轮：「先别写正文，列出你会分哪几步、每步产出什么，等我确认。」
  • 看完计划再补一句「第 2 步改成…」，然后才让它执行。这点人工介入成本极低，收益极高。
  • 同理适用于写代码：先让它说清要改哪几个文件、为什么，再允许它动手。
  • 对于特别长的任务，可以让它每完成一步就停下来等你确认。

✦ 记住：复杂任务拆两步走，错误率降一大截。

# 思维链# 复杂任务# 工作流
03少样本示例，比讲道理管用十倍

模型对「示例」的敏感度，远高于对抽象形容词的敏感度。

  • 写「专业一点」基本没用；贴一段你认为专业的文字，效果立刻可见。
  • 示例要保持格式一致，2～5 个足够，太多会占上下文还容易带偏。
  • 正反例搭配更强：给一个合格样本，再给一个不合格样本并说明差在哪。
  • 做批量任务时，把示例固化成模板，比每次重新描述稳定得多。

✦ 记住：想让它学会某种格式，直接给它看样子。

# Few-shot# 示例# 模板
04把提示词写成模板，而不是一句话

同一个需求第二次出现时，就该把它变成带空格的模板。

  • 用 {{变量}} 占位：{{主题}}、{{受众}}、{{字数}}、{{禁止项}}，用的时候只填空。
  • 给模板配一句「使用说明」和 1 个填好的样例，过一个月回来看还看得懂。
  • 按场景分文件夹管理：写作类、分析类、代码类、复盘类。
  • 版本迭代时留一版旧模板，方便对比哪次改动真的变好了。

✦ 记住：能复用才算资产，否则每次都在重新发明轮子。

03 / AI CODING
叁

AI 编程 · 让 AI 替你写出能跑的东西

先说清楚再动手、让它复述需求、管好上下文，这三招比换更强的模型有用。

3 讲
01AI 写代码的正确姿势：先说清楚，再让它写

把 AI 当成一个能力很强但完全不了解你项目的新同事，就对了。

  • 开工前给三样东西：要达成的目标、涉及的文件/模块、现有的约定（命名、依赖、不能动的地方）。
  • 明确说「不要改哪些文件」，比事后回滚省事。
  • 要求它先输出改动方案，确认后再生成代码；大改动拆成几个小提交。
  • 生成完必须自己跑一遍。能编译不等于逻辑对，尤其涉及边界条件和异常处理。

✦ 记住：需求描述的质量，基本等于产出代码的质量。

# AI Coding# 需求描述
02改代码前，先让它复述需求

「先复述一遍你理解的任务，并列出你打算改动的点，不要写代码。」

  • 复述会暴露理解偏差：把「改按钮颜色」理解成「重构组件」这类事，一问就现形。
  • 发现偏了只需一句话纠正，比代码写完再推倒重来便宜太多。
  • 涉及已有项目时，再追问一句「你觉得哪块风险最高」，常能提前挖出坑。
  • 这条同样适用于让 AI 写文档、做方案、整理表格。

✦ 记住：一个 10 秒的动作，能避免半小时的白干。

# AI Coding# 对齐# 习惯
03上下文管理：一次别塞太多

长对话里最隐蔽的坑，是早期那些已经过时的信息还赖在窗口里。

  • 只贴与当前任务直接相关的代码和报错，不要把整个仓库一股脑丢进去。
  • 报错信息保留完整堆栈，但删掉重复刷屏的部分。
  • 话题切换就开新会话；长会话定期做「到目前为止的结论 + 待办」摘要，然后重开。
  • 如果感觉它开始反复犯同一个错，八成是上下文被污染了，重开比继续解释更快。

✦ 记住：不是给得越多越聪明，混杂的上下文会互相干扰。

04 / AGENTS
肆

AI Agent · 从会聊天到会干活

工具调用、任务闭环、权限刹车，以及什么时候根本不需要多智能体。

4 讲
01Agent 和聊天机器人的分界线

聊天机器人负责「说」，Agent 负责「做」。

  • 最小闭环是：观察 → 决策 → 调用工具 → 拿到结果 → 再决策，直到任务完成或停下。
  • 只有能写文件、查数据库、发请求、调 API，它才真正跨过了那条线。
  • 代价是：每一步都可能出错，错误还会被带到下一步。所以日志和重试机制是刚需。
  • 别为了炫技上 Agent：一次提示词就能搞定的事，用 Agent 只是更慢更贵更不稳。

✦ 记住：能不能自己调用工具、并根据结果决定下一步。

# Agent# 基础概念
02工具调用（Function Calling）是什么

模型并不真的执行操作，它只是输出一个结构化的调用请求，由外面的程序去执行。

  • 你先把可用工具的名称、参数格式、用途描述清楚，模型判断该用哪个、填什么参数。
  • 真正的执行和权限控制在你的代码里，所以安全边界必须由程序兜住，不能指望模型自觉。
  • 工具描述写得好不好，直接决定调用准不准。描述含糊，就会出现乱调或漏调。
  • 返回结果要结构化、可解析，并且对失败情况给出明确信息，模型才能自我纠正。

✦ 记住：让模型从「输出文字」变成「按下按钮」。

# Function Calling# 工具# Agent
03给 Agent 装「刹车」：权限、预算、人工确认

自动化程度越高，越要在关键节点留一道人工闸门。

  • 权限最小化：只读的场合绝不给写权限；能操作测试环境就别碰生产环境。
  • 设硬性上限：最大步数、单次耗时、调用次数、花费预算，超了就强制停。
  • 高风险动作（发消息、付款、删文件、对外发布）一律先弹确认，让人点一下再执行。
  • 全程留痕：每一步的输入、决策、工具结果都记日志，出事能回放。

✦ 记住：能自动跑之前，先想清楚它跑偏了会怎样。

# 安全# 权限# 可靠性
04多智能体协作，什么时候是伪需求

单个 Agent 能把事做对，就别拆。

  • 多 Agent 真正有价值的场景：任务确实可并行、各角色需要不同的工具权限或独立上下文。
  • 常见代价：互相误解、重复劳动、结果不一致、调试困难、成本翻几倍。
  • 很多所谓「多角色协作」，用一个结构良好的长提示词 + 分步骤执行就能达到同样效果。
  • 判断标准很简单：拆开之后，质量或速度有没有可测量的提升？没有就合并回去。

✦ 记住：拆成几个角色听着酷，但复杂度是成倍涨的。

05 / EVALUATION
伍

产品与评估 · 把 Demo 变成有人用的产品

评测集、成本账、兜底与反馈闭环，这才是 AI 产品经理真正的护城河。

3 讲
01怎么判断一个 AI 功能到底好不好

「感觉挺好用」不是指标，上线之后你会为这句话付出代价。

  • 先攒 30～100 条真实用例，覆盖典型场景和边界情况，每条写明期望结果。
  • 分开看：正确性、格式稳定性、响应时间、单次成本、失败时是否优雅降级。
  • 每次改提示词或换模型，都拿同一套用例跑一遍，才知道是变好还是变坏。
  • 线上加一个轻量的反馈入口（点赞/点踩/重新生成），把真实差评回流进评测集。

✦ 记住：别只看 Demo 惊艳，要建一套能重复的评测集。

# 评测# 上线# 指标
02AI 产品的成本账：Token、延迟、缓存

单位成本 × 调用次数 × 平均轮次，这个乘法很容易被低估。

  • 先算清一次典型任务消耗多少输入/输出 Token，再乘以预估日活和轮次。
  • 降本三板斧：缩短系统提示词、对重复内容做缓存、简单任务路由到小模型。
  • 延迟往往是体验杀手。能用流式输出就别让用户干等，能并行就别串行。
  • 给每个用户/会话设额度上限，既控成本也防滥用。

✦ 记住：Demo 里几毛钱的事，跑上量就是另一回事。

# 成本# 延迟# 工程
03从 Demo 到能用：数据、兜底、反馈闭环

中间隔的不是模型能力，是一堆不性感但必须的工程活。

  • 数据：真实输入比想象中脏得多，格式、错别字、超长内容都要处理。
  • 兜底：模型超时、返回格式错、检索没命中时，页面该显示什么、能否重试。
  • 反馈：让用户能低成本地告诉你「这次不对」，并且这些反馈真的会进下一轮优化。
  • 边界：明确告诉用户这个能力不做什么，比默默猜错更能建立信任。

✦ 记住：演示能跑通，和每天都有人用，是两件完全不同的事。

06 / WORKFLOWS
陆

工具与工作流 · 建一条能长期跑的学习流

工具分层、看到就试、用自己的话记下来，让学习真的沉淀成能力。

2 讲
01我的常用 AI 工具分层

工具会换，分层不会。想清楚这一层要解决什么问题，选型就简单了。

  • 对话与思考：通用大模型，用来理清思路、改文字、做初步调研。
  • 写代码与自动化：带代码上下文的编辑器 / Agent，负责把想法落成能跑的东西。
  • 检索与沉淀：知识库、笔记工具、RAG 应用，负责把资料存住并找得回来。
  • 产出与分发：图像、排版、表格、发布渠道。每层固定一两个顺手的就够，不必集邮。

✦ 记住：按用途分四层，不再追着新工具跑。

# 工具# 选型# 心得
02一条能长期跑下去的 AI 学习流

信息不缺，缺的是把「看过」变成「能用」的那一步。

  • 看到新东西先别收藏，当场问自己：它能替掉我现在哪一步重复劳动？答不上就先放过。
  • 答得上就 30 分钟内真跑一次，哪怕只用一个最小例子。跑不通的原因本身就是笔记。
  • 用自己的话写下来，记「适用场景 + 一个坑 + 一个例子」，不复制原文。
  • 定期回看，把还用得上的留下、过时的删掉。这个站就是这么维护的。

✦ 记住：看到 → 试一次 → 记下来 → 用得上，四步闭环。
